# Reminder Howto — Design Spec

**Date:** 2026-08-06
**Status:** Approved (brainstorming complete; awaiting spec review and writing-plans)

## 1. Purpose & Background

The current reminder message shows only the task title, estimated hours, and dependencies. For learning tasks (e.g. Remotion video production), the user needs **actionable how-to steps** in the reminder itself, not just a topic name. The user has 15 tasks in `remotion-finance` already, all of which need step-by-step guidance when their slot fires.

The reminder message is the only place the user is guaranteed to see the task at the moment they need to act. A separate tutorial document requires the user to context-switch away from the message. The howto must be inline.

This spec adds a `task.description` field to the reminder message. The field is already present in the schema (`tasks.description TEXT`) and in `db.create_task()` — but `cli.py task add` doesn't expose it, `task update` doesn't accept it, and `reminder.format_reminder()` doesn't render it. Three small wiring changes plus a backfill.

The user explicitly chose a **two-layer (static + on-demand expansion)** design over pure-static or pure-dynamic:
- **Static** (5-7 numbered steps) is rendered by default in every reminder.
- **On-demand** (full tutorial with code, pitfalls, verification) is generated by Claude when the user replies with a trigger word (`展开` / `详细` / `怎么做`).

Static is cheap, stable, and audit-friendly. Dynamic adds depth on demand without inflating every reminder. The two layers compose: a user who reads only the static layer gets the gist; a user who asks `T001 展开` gets the full tutorial without anyone having to maintain two copies.

## 2. User Constraints (from brainstorming)

| Decision | Value |
|---|---|
| Steps per task (static) | **5-7** numbered actions |
| Storage | `task.description` (existing `tasks.description TEXT` column) |
| Architecture | **Static + dynamic expansion** (Approach C) |
| Trigger words (3 synonyms) | `展开` / `详细` / `怎么做` |
| Cache expanded version? | **No** — every expand request regenerates |
| Where is expand logic? | cc-connect dispatcher recognizes the trigger; Claude generates inline |
| Backfill existing 15 tasks? | **Yes** — one-shot batch on implementation |
| example-goal backfill? | **No** — keep example-goal tasks as-is for backward compat |

## 3. Architecture Overview

Three code changes plus one dispatcher behavior change:

### 3.1 `scripts/cli.py` — expose `task.description` on add/update

- `task add` gains a `--description` flag (default `""`).
- `task update` gains a `--description` flag. The existing `status` argument stays positional (no breakage); description is a separate flag so the call shape becomes `task update <id> <status> --description "..."`. This is non-breaking for existing callers (status is still positional, the new flag is optional).
- The existing `db.create_task()` and the update path already accept description; this is a CLI plumbing change only.
- Validation: description length must be ≤ 2000 characters. Enforced in the CLI; error message: "description too long (max 2000 chars)".

### 3.2 `scripts/reminder.py` — render description in `format_reminder`

Insert a new block after the `🎯 任务` line and before `⏱️ 预计耗时`. If `task.description` is empty, **omit the block entirely** (preserves existing example-goal behavior). If non-empty, render:

```
📝 步骤：
  1. ...
  2. ...
  3. ...
```

Body of the block: split on newlines, strip each line, drop empty lines, prefix with two-space indent + `<n>. `. Cap rendering at 7 lines; if more, append `... (+N more — 回复 "T001 展开" 查看完整版)`.

### 3.3 `tests/test_reminder.py` — two new cases

1. `test_format_reminder_with_description` — passes a task with `description="1. A\n2. B\n3. C"`, asserts the output contains `📝 步骤：` and the three numbered lines, in order.
2. `test_format_reminder_without_description` — passes a task with `description=""`, asserts the output **does not** contain `📝 步骤：` (backward compat for example-goal).

### 3.4 `tests/test_cli.py` — two new cases

1. `test_task_add_with_description` — `cli.py task add ... --description "..."`, then read back via `db.get_task()`, assert description matches.
2. `test_task_update_with_description` — create a task, update with `--description "new"`, read back, assert.

### 3.5 Dispatcher trigger recognition

The cc-connect dispatcher (the Claude that receives user replies) already parses `T001 完成了` / `T001 跳过` / `今日重点 = xxx`. Add a new branch:

- New helper `is_expand_request(text) -> tuple[bool, str | None]`:
  - Returns `(True, task_id)` for inputs matching `T001 展开` / `展开 T001` / `T001 详细` / `T001 怎么做` (and any combination with optional whitespace between).
  - Returns `(False, None)` for everything else.
- Dispatcher flow on user reply:
  1. Run existing task_id parser.
  2. If matched: existing behavior (完成 / 跳过 / 状态更新).
  3. Else: run `is_expand_request`. If matched → read `task.description` via `cli.py task show <id>`, generate expansion, send as Feishu plain message.
  4. Else: fall through to general "user talking to Claude" branch.

**Note**: this dispatcher lives in Claude (cc-connect's downstream Claude session), not in the Python codebase. The change is to Claude's behavioral rules, not to scripts. The Python side is a passive participant (`task show`).

### 3.6 Backfill existing 15 tasks

After the CLI + reminder changes land, generate 5-7 step descriptions for `remotion-finance-T001` … `T015` in one batch (Claude generates the content), then write them via `cli.py task update <id> --description "..."`. Commit the backfill separately so it's traceable.

example-goal tasks (`T001`–`T005`) are not backfilled; their reminders continue to look exactly as today.

## 4. Data Flow

### 4.1 Reminder fire (static layer)

```
cc-connect timer fires
  └─► Claude (cc-connect dispatcher)
        ├─► scripts.cli: scheduler.compute_schedule(focus, date, slot)
        ├─► scripts.cli: db.get_goal / db.get_task
        ├─► scripts.reminder: format_reminder(...)
        │     └─► reads task.description, renders 📝 步骤 block if non-empty
        └─► cc-connect timer add (next slot)
```

### 4.2 User reply (dynamic expansion)

```
User in Feishu: "T001 展开"
  └─► cc-connect (relay)
        └─► Claude (dispatcher)
              ├─► is_expand_request("T001 展开") → (True, "T001")
              ├─► cli.py task show T001   (read task.description)
              ├─► Claude generates expansion (why / code / pitfalls / verify)
              └─► Sends long Feishu plain message
```

## 5. Out of Scope (explicit non-goals)

- Caching the expanded version. Every request regenerates.
- i18n. The howto is in Chinese; no multi-language.
- Mobile vs desktop rendering. Plain Feishu text.
- A/B testing different howto lengths.
- Rich attachments (images, videos) in the expansion.
- Per-goal howto overrides. The trigger is task-scoped only.

## 6. Acceptance Criteria

- [ ] `cli.py task add ... --description "1. A\n2. B"` writes to DB; `task show` returns the description verbatim.
- [ ] `cli.py task update <id> --description "..."` overwrites; same `task show` returns the new value.
- [ ] Reminder for a task with `description=""` contains **no** `📝 步骤：` line (backward compat for example-goal).
- [ ] Reminder for a task with `description="1. A\n2. B\n3. C"` contains `📝 步骤：` followed by three indented numbered lines in order.
- [ ] Reminder for a task with > 7 description lines contains the first 7 + a `... (+N more — 回复 "T001 展开" 查看完整版)` line.
- [ ] User reply `T001 展开` → expansion is delivered as Feishu plain message (not as a new timer).
- [ ] User reply `T001 详细` / `T001 怎么做` → same behavior as `展开`.
- [ ] User reply `展开 T001` / `怎么做 T001` (reverse order) → same behavior.
- [ ] User reply `T001 展开` for a non-existent task → error message, no crash.
- [ ] All 15 remotion-finance tasks have non-empty description after backfill.
- [ ] example-goal tasks remain description="" after backfill; their reminder format is byte-identical to today.
- [ ] All 213 existing tests still pass; 4 new tests pass.

## 7. Risk & Rollback

- **Risk**: rendering change to `format_reminder` could shift column alignment in `cli.py today` output, or break any test that does a literal `assertIn` on the full reminder string.
  - **Mitigation**: existing tests use substring matchers; spec explicitly checks backward compat for empty-description case.
- **Risk**: dispatcher might mis-parse `T001 详细` as a status update (it doesn't start with `完成` or `跳过`, so should be safe — but Chinese parsing has edge cases).
  - **Mitigation**: trigger-word set is closed (3 words). The parser treats these as **expand** when the existing task-status parser doesn't match first.
- **Rollback**: revert the 3 commits (CLI, reminder, tests) + revert backfill commit. The schema is unchanged; no migration needed.

## 8. Open Questions for Plan Phase

- Exact position of `📝 步骤` block: between `🎯 任务` and `⏱️ 预计耗时` is the spec's proposal. Plan phase can adjust if Feishu readability tests suggest otherwise.
- Whether the description cap (2000 chars) lives in the CLI or in `db.create_task` validation. Spec proposes CLI (early failure, clear error message).
- Whether the dispatcher trigger-recognition lives in a Python helper (testable) or in Claude's prompt (not testable). Spec recommends Python helper; plan can revisit.
